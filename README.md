# Digital Wallet & Transaction Processing Platform

A production-oriented REST API for a digital wallet: wallets, deposits, withdrawals, peer-to-peer transfers, an immutable
double-entry-style ledger, refunds, rule-based fraud monitoring, notifications, scheduled processing, audit logging and
role-based dashboards.

**Stack:** Python 3.12 - FastAPI - PostgreSQL 16 - SQLAlchemy 2 - Alembic - Pydantic v2 - Pytest
(optional: Celery + Redis, Docker / Docker Compose)

Priorities, in order: **financial data integrity -> security -> transaction correctness -> concurrency -> idempotency
-> business-rule enforcement -> clean architecture -> tests -> API quality.**

## 1. Quick start

### Option A - local
```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env                       # then edit SECRET_KEY / DATABASE_URL

# PostgreSQL (create role + database once)
createuser -P wallet                        # password: wallet   (or use your own and edit .env)
createdb -O wallet wallet_db

alembic upgrade head                        # creates all tables, triggers, roles, default limits
python -m scripts.seed                      # creates the Super Admin from SEED_ADMIN_* in .env
uvicorn app.main:app --reload               # http://localhost:8000/docs
```

### Option B - Docker Compose
```bash
docker compose up --build                   # db + redis + api (migrates & seeds on start)
docker compose --profile celery up          # + Celery worker & beat (scheduled jobs)
```
> The Docker files are provided but **were not built in the authoring environment** (no Docker daemon there) - see
> [section 13](#13-verification-status--known-limitations).

### First calls
```bash
# 1. register (customers self-register; staff are created by a Super Admin)
curl -X POST localhost:8000/api/auth/register -H 'content-type: application/json' \
  -d '{"email":"alice@example.com","full_name":"Alice Sharma","password":"StrongPass123"}'
# 2. login -> access_token / refresh_token
# 3. create wallet, deposit (needs an Idempotency-Key), transfer ... see docs/API.md or import the Postman collection
```
Seeded Super Admin: `superadmin@example.com` / `ChangeMe123!` (**change it** via `.env` before seeding anywhere real).

**Postman:** import `postman_collection.json`, set `baseUrl`, run folder **Quick Start** top to bottom - 53 requests with
84 assertions that exercise register -> login -> RBAC -> deposit -> idempotent replay -> transfer -> limits -> held transfer
-> staff approval -> refund -> freeze -> dashboards -> audit -> token rotation -> logout.

## 3. Concurrency strategy

The requirement: a wallet holds INR 1,000; request A transfers 800 and request B transfers 700 *at the same time* -
**both must not succeed**. Defence in depth, from the application down to the database:

1. **One DB transaction per use-case.** A transfer's debit, credit, both ledger rows, status changes, audit rows,
   notifications and idempotency record commit together or not at all. Services own the transaction boundary.
2. **Pessimistic row locking (`SELECT ... FOR UPDATE`).** Before any balance is read or changed, the involved wallet rows
   (and their balance rows) are locked and **re-read** (`populate_existing`). A competing request blocks until the first
   commits, then sees the new balance: the 800 transfer succeeds, the 700 one then sees 200 and fails with
   `INSUFFICIENT_BALANCE`. Pessimistic locking was chosen over optimistic versioning because contention on a single
   wallet is expected and the loser should wait and re-evaluate, not retry.
3. **Deterministic lock ordering.** Wallets are locked in ascending-UUID order, so `A -> B` and `B -> A` transfers
   running simultaneously can never deadlock (verified by a test with 20 opposing transfers).
4. **Limits are evaluated under the lock.** Daily totals / counts are computed from `transactions` *while the sender
   wallet is locked*, so two parallel requests cannot both slip under a daily limit.
5. **Single choke point for money.** Only `LedgerService` changes balances. It checks `spendable = available - pending`
   and writes the ledger row (`balance_before`/`balance_after`) in the same call.
6. **Database constraints as the last line of defence.** `CHECK available_balance >= 0`, `pending_balance >= 0`,
   `pending_balance <= available_balance`, ledger arithmetic CHECK, partial-unique refund index, unique references.
   Even a bug in application logic cannot persist a negative balance or a double refund.
7. **Isolation level:** PostgreSQL's default `READ COMMITTED` is sufficient *because* correctness relies on explicit row
   locks and constraints rather than on snapshot reads. (`SERIALIZABLE` would add retry loops for no extra safety here.)
8. **Lock order across aggregates** is `suspicious record -> transfer/withdrawal -> wallets`, used consistently by
   approve / reject / cancel / cleanup so those paths cannot deadlock each other.

What is prevented: **negative balances** (2, 5, 6), **double spending** (2, 5 + reservations in section 5),
**lost updates** (2 - the receiver is locked too), **duplicate transactions** (section 4, and the refund unique index).

**Proof, not just argument:** `tests/test_concurrency.py` fires truly parallel requests (threads released by a barrier)
at real PostgreSQL. It includes the exact 800/700 scenario, 20 transfers racing for 1,000, concurrent withdrawals,
mixed transfers + withdrawals, 20 parallel deposits (no lost updates), 10 senders crediting one receiver, opposing
transfers (deadlock check), 8 parallel requests sharing one idempotency key, parallel duplicate refund requests,
parallel refund approvals and parallel review approvals. **Mutation check performed:** with the `FOR UPDATE` clauses
removed, 7 of these 13 tests fail (including the 800/700 case and the lost-update tests); with locking restored all pass.

## 4. Idempotency

`POST` deposit / withdrawal / transfer / refund **require** an `Idempotency-Key` header (400 `IDEMPOTENCY_KEY_REQUIRED`
otherwise).

| Situation | Result |
|---|---|
| New key | Executed; response stored with the key |
| Same key + same payload | Stored response **replayed** verbatim, header `Idempotent-Replayed: true`, nothing re-executed |
| Same key + different payload | `409 DUPLICATE_IDEMPOTENCY_KEY` |
| Same key, concurrent requests | The loser blocks on the unique index, then replays the winner's response |
| Request that failed *before* any record was created (e.g. frozen wallet) | Transaction rolled back, **key not consumed** - the client may retry with the same key |
| Request that produced a recorded failure (insufficient balance, limit) | Failure persisted and **replayed** identically on retry |

Mechanics: table `idempotency_keys` with `UNIQUE (user_id, scope, key)` and a SHA-256 of the canonical payload. The key row
is inserted (`INSERT ... ON CONFLICT DO NOTHING`) **inside the same transaction** as the money movement - so the key exists
if and only if the movement committed. Keys are scoped per user and per operation. Expired keys are purged by the
`pending_cleanup` job (default TTL 48 h).

## 5. Ledger & balance model

* **`transaction_ledger`** - one immutable row per balance change: wallet, type (`DEPOSIT`, `WITHDRAWAL`,
  `TRANSFER_DEBIT`, `TRANSFER_CREDIT`, `REFUND`, `FEE`, `ADJUSTMENT`, `REVERSAL`), direction, amount, `balance_before`,
  `balance_after`, reference entity/id, description, `created_by`, timestamp, JSONB metadata.
  *Immutability is enforced three ways:* a PostgreSQL `BEFORE UPDATE OR DELETE` trigger, an ORM event guard, and no API
  endpoint that mutates it. The same applies to `audit_logs`. (`FEE`/`REVERSAL` are modelled in the type enum; no endpoint
  generates them - see limitations.)
* **Invariant:** for every wallet, `available_balance == sum(CREDIT) - sum(DEBIT)` over its ledger. Concurrency tests assert it.
* **`pending_balance`** = funds *reserved* for outgoing transactions that are held for review. `spendable = available - pending`.
  Reserving makes held money unspendable (no double spend) without writing a ledger row, because the *available* balance
  has not changed yet. The ledger row is written when the transaction settles. On cancel / reject, the reservation is released.
* **`transactions`** (unified business record) powers history, filtering, limits and monitoring and is what refunds reference.
* **Atomic transfers:** debit + credit + both ledger rows + status flips happen in one DB transaction.
* **Failed transfers never reduce the sender's balance** - the FAILED attempt is recorded for history/audit, nothing is debited.

## 6. State machines

Declared once in `app/domain/state_machines.py`; services never assign `.status` directly. Diagrams in
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

* **Wallet:** `ACTIVE <-> FROZEN`, `ACTIVE/FROZEN/SUSPENDED -> CLOSED` (terminal); invalid transitions -> `409 INVALID_STATE_TRANSITION`.
  Who may do what: owners can freeze or close (balance must be 0) their own wallet; **unfreeze needs staff**; support agents can
  freeze/unfreeze; only admins can suspend / reactivate / change arbitrary status.
* **Deposit / Withdrawal / Transfer:** `PENDING -> PROCESSING -> COMPLETED | FAILED`, `PENDING -> CANCELLED`, and a bounded
  `FAILED -> PROCESSING` retry (gateway timeouts only).
* **Refund:** `REQUESTED -> UNDER_REVIEW -> APPROVED -> COMPLETED | FAILED`, or `-> REJECTED`.

## 7. Limits & suspicious-transaction monitoring

Admins configure everything in `GET/PATCH /api/admin/transaction-limits` (changes are audited with before/after):
max transaction amount, daily transfer limit, daily withdrawal limit, max transactions per day, plus the monitoring thresholds.
Limit violations are rejected with `TRANSACTION_LIMIT_EXCEEDED`.

Every outgoing transfer/withdrawal is risk-scored under the wallet lock:

| Rule | Outcome |
|---|---|
| Amount > max / daily limit exceeded / daily count exceeded | **BLOCKED** - rejected (`TRANSACTION_LIMIT_EXCEEDED`), FAILED record + suspicious record + staff notification + audit `TRANSACTION_BLOCKED` |
| >= `velocity_block_count` transactions inside the window | **BLOCKED** (`SUSPICIOUS_TRANSACTION`, 403) |
| Amount >= `suspicious_amount_threshold` | **REVIEW_REQUIRED** |
| >= `velocity_review_count` in the window ("multiple transfers in a short period") | **REVIEW_REQUIRED** |
| >= `frequency_review_threshold` today ("unusual frequency") | **REVIEW_REQUIRED** |
| Wallet frozen within `recently_frozen_hours` | **REVIEW_REQUIRED** |

`REVIEW_REQUIRED` transactions return **`202`**, stay `PENDING` with the funds **reserved**, and notify staff. Support/Admin review
them via `POST /api/admin/suspicious-transactions/{id}/review` (`APPROVE` settles atomically; `REJECT` releases the hold).
The sender may also cancel while pending. Held items are auto-cancelled after `PENDING_REVIEW_TIMEOUT_HOURS`.

## 8. Authentication & authorization

* **JWT** access (15 min) + refresh (7 d) tokens; bcrypt password hashing; strength rules (>= 8 chars, upper/lower/digit).
* **Refresh-token rotation:** every refresh issues a new refresh token and revokes the old one. **Reuse of a rotated token
  revokes the entire session family** (theft detection).
* **Revocation:** access tokens embed the session (family) id and are checked against it on every request, so **logout,
  password change and user deactivation invalidate access tokens immediately**, not at expiry.
* **Inactive users cannot log in** (`ACCOUNT_INACTIVE`) and existing sessions die on deactivation.
* Login timing is equalised for unknown e-mails; failed logins are audited.
* **Roles:** `SUPER_ADMIN`, `ADMIN`, `SUPPORT_AGENT`, `CUSTOMER` - enforced by `require_roles` (role-based) plus ownership checks in
  services (resource-based: wallet ownership, transfer participants, refund requester, transaction visibility).
  The exact role required by each endpoint is listed in [`docs/API.md`](docs/API.md) (generated from the code).

## 9. Scheduled processing

`app/jobs/tasks.py` - plain functions, runnable from Celery Beat (`app/celery_app.py`), cron, tests, or
`POST /api/admin/jobs/{name}/run` (Admin).

| Job | What it does |
|---|---|
| `daily_limit_reset` | Daily limits are computed over a UTC-day window, so they reset implicitly at 00:00 UTC; the job records the roll-over (audit) |
| `pending_cleanup` | Cancels stale PENDING deposits and over-age held transfers/withdrawals (releasing reserved funds); purges expired idempotency keys and old refresh tokens |
| `suspicious_scan` | Post-hoc scan for velocity / daily-frequency bursts that slipped past request-time checks; flags the latest unflagged transaction |
| `daily_wallet_summary` | One `DAILY_SUMMARY` notification per active wallet per day (idempotent) |
| `failed_transaction_retry` | Bounded retry (`MAX_RETRY_ATTEMPTS`) of `GATEWAY_TIMEOUT` failures; permanent failures are never retried |
| `daily_transaction_report` | Aggregates yesterday's count / failures / volume into an audit record |

Notification **delivery** uses FastAPI `BackgroundTasks` (after the response); the notification rows themselves are written in the
business transaction so they are never lost or sent for rolled-back work.

## 12. Design decisions & assumptions

* **Money** is `NUMERIC(18,2)` / `Decimal`, serialised as strings. Max 2 decimal places, must be `> 0` (422 otherwise).
* **Pending / reserved model.** `pending_balance` reserves part of `available_balance` for held outgoing transactions (see section 5).
* **Held transactions** (review-required) return `202` and make `cancel` endpoints meaningful; non-flagged operations settle immediately.
* **Refund** = reversal of a `COMPLETED` **transfer**, requested by the original sender, approved by staff; funds move receiver -> sender.
  At most **one live refund per transaction** (partial refunds allowed, but a single one). Refunds of deposits/withdrawals are rejected (`INVALID_REFUND`).
  If the receiver has already spent the money, approval ends in `FAILED / INSUFFICIENT_BALANCE` (no money moves) and the slot is freed.
* **"Users cannot transfer to themselves"** is enforced at *user* level - transfers between two wallets of the same user are also rejected.
* **Deposits** require an `ACTIVE` wallet (frozen wallets cannot receive money either, consistent with the receiver rule for transfers).
* **Failures are recorded.** Insufficient balance / limit / block outcomes persist a `FAILED` record (history, audit, notification) and return the error.
  Pure validation errors (frozen wallet, unknown wallet, bad ownership) create nothing and do not consume the idempotency key.
* **Limits are global** (singleton row) and expressed as plain numbers applied to the wallet currency; they are tracked **per wallet per UTC day**
  (this keeps the check race-free under the wallet lock).
* **Payment gateway is simulated.** `simulate_outcome` (`SUCCESS|FAILURE|TIMEOUT`) is a test hook; turn it off with `ALLOW_SIMULATION=false`.
* **Customers only own wallets**; staff cannot create wallets and cannot become wallet owners (a user with wallets cannot be given a staff role).
* **Wallet `PATCH`** accepts `name` and `status` (status goes through the same permission matrix and state machine as freeze/unfreeze).
* **Extras beyond the brief:** `GET /api/wallets/{id}/ledger`, `GET /api/transactions/{id}[/ledger]`, `POST /api/refunds/{id}/start-review`
  (to reach `UNDER_REVIEW`), admin user management, Super-Admin balance adjustments (ledger-backed `ADJUSTMENT`), on-demand job runner, Celery wiring.

## 13. Verification status & known limitations

**Verified in the authoring environment** (PostgreSQL 16, Python 3.12):
* 258 automated tests pass, 97% line coverage; concurrency tests were run repeatedly (stable) and mutation-checked (they fail without the locks).
* Migration: `upgrade -> downgrade base -> upgrade` round-trips; `alembic check` shows no model/migration drift; triggers reject UPDATE/DELETE on ledger & audit.
* App run live under `uvicorn` against a freshly migrated + seeded database; the Postman **Quick Start** folder was executed with Newman:
  53 requests, 84 assertions, 0 failures.
* The Mermaid diagrams (ER + architecture) were checked with the Mermaid parser; `docs/API.md` examples are real captured responses.

**Not verified / limitations - be aware:**
* **Docker / Docker Compose files were not built or run** (no Docker daemon available). The entrypoint script and the compose YAML structure were checked, nothing more.
* **Celery + Redis were not run end-to-end** (no Redis). The Celery app imports and registers all 7 tasks; the jobs themselves are fully tested as plain functions.
* Not implemented (listed as optional in the brief): Redis distributed locking / caching, WebSocket & e-mail notifications (delivery is a logged simulation),
  rate limiting, Prometheus metrics, CSV export, CI/CD. `FEE` and `REVERSAL` ledger types exist in the schema but no endpoint produces them.
* Multi-currency: wallets/transfers are single-currency (cross-currency transfers are rejected); limits are not currency-converted.
* Load/performance testing was not performed beyond the parallel correctness tests; indexes were designed for the documented query patterns.
* Production hardening still to do for a real deployment: secrets management, TLS termination, CORS policy, rate limiting / account lockout, DB role with
  `REVOKE UPDATE, DELETE` on the ledger/audit tables (the trigger already blocks it), backups, and structured log shipping.
